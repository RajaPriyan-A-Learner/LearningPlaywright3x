What it is

A callback is a function passed as an argument to another function, invoked once that function completes its work — synchronously (e.g. Array.map) or asynchronously (e.g. fs.readFile, setTimeout). It's the original async primitive JS shipped with; Promises and async/await are built to solve callbacks' composability problems, not to replace the mechanism underneath.

Error-first convention (Node.js)

fs.readFile('./config.json', 'utf8', (err, data) => {
  if (err) {
    // err is always the first argument — check it first
    return console.error('Read failed:', err);
  }
  console.log(JSON.parse(data));
});

Callback hell

getUser(id, (err, user) => {
  getOrders(user.id, (err, orders) => {
    getInvoice(orders[0].id, (err, invoice) => {
      emailInvoice(invoice, (err, res) => {
        // pyramid of doom: 4 levels deep,
        // error handling duplicated at every level,
        // impossible to Promise.all these in parallel
      });
    });
  });
});
Why it breaks down: nesting couples control flow to indentation, error handling is copy-pasted at every level, and there's no way to run steps concurrently without restructuring everything.

Fix: named functions or Promisify

const readFileAsync = util.promisify(fs.readFile);
// now composable with .then chains or await

The three states

  • pending — initial state, neither fulfilled nor rejected.
  • fulfilled — resolve(value) was called; state is locked forever.
  • rejected — reject(reason) was called; state is locked forever.

Once settled (fulfilled or rejected), a promise can never change state again — that immutability is what makes it safe to hand a promise to multiple consumers.

Constructing one

const p = new Promise((resolve, reject) => {
  // executor runs SYNCHRONOUSLY, immediately
  doAsyncWork((err, result) => {
    if (err) return reject(err);
    resolve(result);
  });
});
Interview trap: the executor function itself runs synchronously the instant new Promise() is called — only the settlement (and anything chained with .then) is deferred to the microtask queue.

Promise constructor anti-pattern

// ❌ wrapping something that's already a promise
function getData() {
  return new Promise((resolve, reject) => {
    fetch('/api/data')
      .then(res => resolve(res))
      .catch(err => reject(err));
  });
}
// ✅ fetch already returns a promise — just return it
function getData() {
  return fetch('/api/data');
}

Chaining & the "forgot to return" bug

getUser(id)
  .then(user => {
    getOrders(user.id); // ❌ not returned
  })
  .then(orders => {
    // orders is undefined — the chain didn't wait
    // for getOrders(), it moved on immediately
  });
Rule: every .then() must return a value or a promise, or the next link in the chain gets undefined instead of waiting.

What it really is

Syntactic sugar over promises. An async function always returns a promise — if you return 5, callers see Promise<fulfilled: 5>. await pauses the async function's execution (not the thread) until the awaited promise settles, then resumes as a continuation on the microtask queue.

try/catch replaces .catch()

async function loadUser(id) {
  try {
    const res = await fetch(`/users/${id}`);
    if (!res.ok) throw new Error('Bad response');
    return await res.json();
  } catch (err) {
    logger.error(err);
    throw err; // re-throw so caller's promise still rejects
  }
}

The sequential-await trap

// ❌ 3 round-trips, run one after another (slow)
const a = await fetchA();
const b = await fetchB();
const c = await fetchC();

// ✅ fire all three, then wait — parallel
const [a2, b2, c2] = await Promise.all([
  fetchA(), fetchB(), fetchC()
]);
Why this shows up in interviews: it's the single most common real-world async/await performance bug — independent requests get serialized by accident because await is used inline instead of started concurrently.

Sync-until-first-await

async function f() {
  console.log('A');       // runs synchronously
  await null;             // suspends here, yields to microtask queue
  console.log('B');       // resumes later, as a microtask
}
console.log('start');
f();
console.log('end');
// output: start, A, end, B

Behavior

  • Runs all input promises concurrently.
  • Resolves when every promise fulfills, with results in the same order as input — not completion order.
  • Fail-fast: rejects immediately on the first rejection, even if other promises are still pending. Their eventual results are discarded (though the promises still run to completion — you just stop hearing about them).

Typical use

const [profile, orders, prefs] = await Promise.all([
  fetchProfile(userId),
  fetchOrders(userId),
  fetchPreferences(userId),
]);
// dashboard needs all three — one failing means
// there's nothing useful to render anyway

allSettled example

const results = await Promise.allSettled([
  pingService('auth'), pingService('billing')
]);
results.forEach(r => {
  if (r.status === 'fulfilled') console.log(r.value);
  else console.warn(r.reason);
});

Behavior

Settles as soon as the first input promise settles — whether that's a fulfillment or a rejection. "Race" means first-past-the-post, win or lose; it doesn't care which.

Timeout pattern

function withTimeout(promise, ms) {
  const timeout = new Promise((_, reject) =>
    setTimeout(() => reject(new Error('Timed out')), ms)
  );
  return Promise.race([promise, timeout]);
}

await withTimeout(fetch('/slow-endpoint'), 3000);
// rejects with 'Timed out' if fetch takes longer than 3s —
// note: the slow fetch keeps running in the background,
// race() doesn't cancel it. Pair with AbortController to truly cancel.

Promise.race vs Promise.any

Promise.racePromise.any
Settles onfirst settle — fulfill or rejectfirst fulfill only
All rejectrejects with first rejection reasonrejects with AggregateError
Use whentimeouts, "whichever finishes first"redundant sources — first success wins
Common confusion: race can reject on the first settle even if a later promise would have fulfilled. any is what you actually want for "try multiple mirrors, use whichever succeeds first."

The model that explains all five topics above

Callbacks, Promises, and async/await are all just different ways of scheduling work onto the same underlying machinery. There is exactly one JS call stack (single-threaded), and two queues the event loop drains once the stack is empty.

Call Stack
console.log('4')
main()
Web API / Node API
setTimeout(fn, 0) timer
Microtask Queue
Promise.then callback
async fn continuation
Event loop rule: after each call-stack frame finishes, drain the entire microtask queue (Promises, async/await continuations, queueMicrotask) before pulling even one task from the macrotask / callback queue (setTimeout, setInterval, I/O, UI events).
1. Sync code (call stack)→ 2. Drain microtasks fully→ 3. One macrotask→ 4. Drain microtasks again→ …repeat

Worked trace

console.log('1');
setTimeout(() => console.log('2'), 0);
Promise.resolve().then(() => console.log('3'));
console.log('4');
// output: 1, 4, 3, 2

1run console.log('1')—emptyempty
2setTimeout registers timer, returns immediately—empty[log '2']

Why this matters for testing: flaky-test root cause #1 in async UI code is exactly this — an assertion running before a microtask (state update from a resolved fetch) or macrotask (a debounce/setTimeout) has drained. Fixing it usually means awaiting a resolved promise or flushing timers, not adding arbitrary sleeps.
