1. Callback Functions

At the lowest level of JavaScript's asynchronous capabilities lies the callback. Because JavaScript is single-threaded and runs on a non-blocking Event Loop, operations like Network Requests (I/O) or timers must not block the main execution thread.

A callback is simply a function passed as an argument to another function, intended to be invoked ("called back") at a later time. When dealing with asynchronous APIs (like setTimeout or Node's fs.readFile), the callback is handed off to the Web APIs / C++ APIs and placed onto the Task Queue (Macro-task queue) once the operation finishes.

// The classic asynchronous callback pattern
function fetchData(id, callback) {
    console.log(`Fetching data for ${id}...`);
    setTimeout(() => {
        const data = { id: id, name: "Premium User" };
        callback(null, data); // Error-first callback pattern
    }, 1000);
}

fetchData(42, (err, result) => {
    if (err) return console.error(err);
    console.log("Data received:", result);
});

The Dark Side: Inversion of Control & Callback Hell

Callbacks suffer from two major flaws. First, Callback Hell (Pyramid of Doom), where sequential async operations create deep horizontal nesting. Second, and more critically, Inversion of Control. When you pass a callback to a third-party library, you surrender control of your program's execution. You must trust that the library will call your function exactly once, not multiple times, and with the correct context.

A callback is a function passed as an argument to another function, which is then executed inside the outer function to complete some kind of routine or action. They can be synchronous (like in Array.map()) or asynchronous (like in setTimeout()).
Inversion of Control happens when you write a callback and hand it to another part of the system (like a 3rd-party library) to execute. You lose control over when and how many times that callback is executed. The library could have a bug and call your payment-processing callback twice. Promises solve this by returning the control back to the caller (a Promise can only be resolved once).

2. new Promise

A Promise is an object representing the eventual completion (or failure) of an asynchronous operation and its resulting value. It acts as a proxy for a value not necessarily known when the promise is created.

Promises solved the Inversion of Control problem. Instead of handing a callback to a function, the function returns a Promise object to you. You maintain control and attach your callbacks (.then(), .catch()) to that object. Promises utilize the Microtask Queue, which has higher priority than the standard Task Queue used by setTimeout.

// Creating and consuming a Promise
const paymentProcessor = new Promise((resolve, reject) => {
    let success = true;
    setTimeout(() => {
        if (success) {
            resolve({ transactionId: "TRX-999", status: "Paid" }); // Transitions to FULFILLED
        } else {
            reject(new Error("Payment Gateway Timeout")); // Transitions to REJECTED
        }
    }, 1500);
});

paymentProcessor
    .then(data => console.log("Success:", data))
    .catch(err => console.error("Failed:", err.message))
    .finally(() => console.log("Transaction pipeline closed."));

State Machine

A Promise is a state machine with three states: Pending, Fulfilled, and Rejected. It is immutable once settled. Calling resolve() multiple times has no effect after the first call.

Zero-to-Hero Interview Questions

Nothing happens on the second call. A Promise can only settle once. Once it transitions from "Pending" to "Fulfilled" (or Rejected), its state and value are locked permanently. Subsequent calls to resolve() or reject() are silently ignored.
This is due to the Event Loop architecture. Promise callbacks are pushed to the Microtask Queue, whereas setTimeout callbacks go to the Macro-task (Task) Queue. The Event Loop completely drains the Microtask queue immediately after the current synchronous code finishes, before it even looks at the Macro-task queue.

3. Promise.all()

Promise.all() is the cornerstone of parallel asynchronous execution in JavaScript. It takes an iterable (usually an array) of Promises and returns a single new Promise. This new Promise resolves when all of the input's promises have resolved, or it rejects immediately if any of the input promises reject.

const fetchUser = fetch('/api/user');
const fetchPosts = fetch('/api/posts');
const fetchConfig = fetch('/api/config');

// Executes concurrently, vastly improving performance over sequential awaiting
Promise.all([fetchUser, fetchPosts, fetchConfig])
    .then(([userRes, postsRes, configRes]) => {
        // Output array matches the EXACT order of the input array,
        // regardless of which promise finished first.
        console.log("All data loaded concurrently!");
    })
    .catch(err => {
        // "Fail-fast" behavior: If fetchPosts fails, the whole block fails instantly.
        console.error("One of the APIs failed:", err);
    });

Zero-to-Hero Interview Questions

The resulting array of values maintains the exact same order as the original input array of Promises, regardless of the order in which the Promises actually resolved under the hood.
Historically, developers mapped over the array and attached a .catch() to each individual promise before passing them to Promise.all (so they resolve with an error object instead of rejecting). Modern JavaScript introduced Promise.allSettled() specifically for this use case, which waits for all promises to finish regardless of success or failure.

4. Promise.race()

While Promise.all waits for everyone, Promise.race() waits for no one. It returns a Promise that settles (resolves or rejects) as soon as the very first Promise in the iterable settles.

The most practical real-world application for Promise.race is implementing Timeouts for network requests, as the native fetch API historically did not support timeouts easily.

const fetchData = fetch('https://slow-api.com/data');

const timeout = new Promise((_, reject) => {
    setTimeout(() => reject(new Error("Request Timed Out!")), 3000);
});

// The race is on! Whichever settles first wins.
Promise.race([fetchData, timeout])
    .then(response => console.log("Data fetched in time!", response))
    .catch(err => console.error("Race over:", err.message)); 
    // If fetchData takes > 3s, the timeout rejects first.

Zero-to-Hero Interview Questions

The fetch request continues running in the background. Promise.race does not cancel or abort the losing Promises; it simply ignores their results. To actually cancel the network request, you must use an AbortController and pass its signal to the fetch call.

5. Async

The async keyword, introduced in ES2017, is syntactic sugar over Promises and Generator functions. Adding async before a function declaration does two critical things under the hood:

  1. It allows the use of the await keyword inside the function body.
  2. It forces the function to always return a Promise. If you return a primitive value, JavaScript automatically wraps it in Promise.resolve().
async function getUsername() {
    // Looks like returning a string, but actually returns Promise.resolve("admin")
    return "admin"; 
}

// You cannot do: const name = getUsername();
// You MUST consume it as a Promise:
getUsername().then(name => console.log(name));

Technically, no. Even if you write return "Hello";, the JS engine intercepts this and transforms it into return Promise.resolve("Hello");. The caller always receives a Promise object.

6. Await

The await keyword is what makes async powerful. It pauses the execution of its surrounding async function until the Promise it is waiting on settles. It completely eliminates the need for .then() callbacks, allowing asynchronous code to read like top-to-bottom synchronous code.

Critically, await does not block the main thread. It only suspends the local execution context of that specific async function. The rest of the JavaScript application continues to run.

async function performComplexFlow() {
    try {
        // Execution pauses here. Event loop goes to do other things.
        const auth = await authenticateUser(); 
        
        // Only runs AFTER authenticateUser resolves
        const data = await fetchDashboard(auth.token);
        
        console.log("Dashboard loaded", data);
    } catch (error) {
        // Await beautifully integrates with standard try/catch!
        // This catches BOTH sync errors and async Promise rejections.
        console.error("Flow failed:", error);
    }
}

When an engine hits an await, it evaluates the expression on the right. If it's a Promise, it suspends the function and yields control back to the caller (sync code continues). The rest of the async function (the code after the await) is packaged as a Microtask and placed on the Microtask Queue to be executed only after the call stack is completely empty.
