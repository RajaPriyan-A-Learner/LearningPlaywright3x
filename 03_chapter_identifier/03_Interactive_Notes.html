⚖️ The Identifier Rules

Identifiers (names for variables/functions) must start with a Letter, an Underscore `_`, or a Dollar sign `$`. They can NEVER start with a digit!

Naming Syntax
let _private = "Valid";  // ✅
let $price = 99;         // ✅
let item1 = "Valid";     // ✅

// Syntax Errors!
// let 1stPlace = "No";  // ❌ Starts with digit
// let my-name = "No";   // ❌ Hyphens forbidden

🔠 Absolute Case Sensitivity

JavaScript evaluates identifiers with extreme case-sensitivity. `totalamount` and `totalAmount` are two entirely separate places in memory. This is the #1 cause of ReferenceErrors!

Case Sensitivity
let userName = "Raja";
let UserName = "Priyan";

console.log(userName); // Raja
console.log(username); // 💥 ReferenceError!

📖 Standard Conventions

While JavaScript lets you name things however you want, professional teams enforce strict casing: `camelCase` for vars/functions, `PascalCase` for classes, and `SCREAMING_SNAKE` for constants.

Industry Standards
let isLoggedIn = true;       // camelCase (Variables)
function getUser() {}        // camelCase (Functions)

class ShoppingCart {}        // PascalCase (Classes)

const MAX_RETRIES = 5;       // SCREAMING_SNAKE (Constants)

⚠️ Reserved Keyword Gotcha

You cannot use words reserved by the language (like `if`, `class`, `function`). But because JS is case-sensitive, `If` and `Function` are technically valid identifiers (though heavily frowned upon!).

Keyword Quirks
// let function = "x"; // ❌ SyntaxError

// Capital 'F' makes it a new identifier!
let Function = "x";    // ✅ Valid (but terrible!)
let Let = 5;           // ✅ Valid (but terrible!)
Practical Application

Real World & Common Mistakes

🛠️ Real-World Use Case

JSDoc Comments: Standard `//` comments are ignored. But `/** */` comments are read by IDEs (like VS Code) to provide IntelliSense, autocomplete, and hover-documentation for your team!

Practical Example
/**
 * Calculates the sum of two numbers.
 * @param {number} a - First number
 * @param {number} b - Second number
 * @returns {number} The sum
 */
function add(a, b) {
    return a + b;
}

❌ Common Developer Mistake

The Pseudo-Private `_` Prefix: Developers often prefix variables with `_` to signal they are "private". This is just a gentleman's agreement; it does NOT prevent external code from mutating the value!

Common Mistake
class User {
    constructor() {
        this._password = "secret"; // Just a convention
    }
}
let u = new User();
u._password = "hacked"; // 💥 Still fully accessible!

// Use true ES2022 private fields instead: #password

Interview Preparation

Q1: Do lots of comments slow down JavaScript execution performance?
No! Comments have absolutely zero runtime cost. The JavaScript parser completely strips all comments out of the code before the execution or JIT compilation phase even begins. Over-commenting is only a readability issue, not a performance one.
Q2: Which of these are invalid identifiers and why? `1stPlace`, `_private`, `first-name`, `$user`
`1stPlace` is invalid because identifiers cannot start with a digit. `first-name` is invalid because hyphens (`-`) are not allowed (the engine interprets it as a subtraction operator). `_private` and `$user` are perfectly valid.
Q3: Why shouldn't you name a variable `__proto__`?
While syntactically allowed, `__proto__` is a historic, special property that directly accesses and mutates the prototype chain of an object. Assigning to it changes how the object inherits methods, leading to massive performance drops and severe bugs.
